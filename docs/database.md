# Database foundation — Phase 1

## Goal and current scope

Prepare PostgreSQL persistence before exposing link creation or redirects. This
phase adds a Prisma schema, a versioned SQL migration, server-only database access,
and integration tests. The introduction page still needs no database connection.

## Schema and connection design

`prisma/schema.prisma` defines one `Link` model:

| Field            | PostgreSQL type          | Purpose                                                     |
| ---------------- | ------------------------ | ----------------------------------------------------------- |
| `id`             | UUID primary key         | Internal identity, generated by Prisma when creating a link |
| `code`           | Unique varchar(32)       | Lookup key; the unique index also prevents collisions       |
| `destinationUrl` | Text                     | Full destination, including query string and fragment       |
| `createdAt`      | Timestamp with time zone | Creation time, defaulted by PostgreSQL                      |

The 32-character column is a storage limit, not a promise about public code length.
URL validation, code generation, HTTP responses, and collision retries belong to
Phase 2. Expiry, ownership, and click records will be added with their features.

Prisma CLI, Client, and the PostgreSQL adapter are pinned to **7.10.1**. Prisma's
`latest` tag currently selects version 8's release candidate with a different
API; use the project's npm scripts rather than installing an unpinned CLI. See
[Prisma release status](https://www.prisma.io/docs/orm/release-status).

`src/lib/db.ts` exports `getDb()`. It checks configuration on first use, creates
one client per process, and reuses it through development hot reloads. The `pg`
pool is limited to two connections, with 10-second connection and idle timeouts.
Each serverless instance has its own pool; this does not impose a global limit.
Use Neon's pooled connection for deployed requests. The `server-only` marker
prevents this module from entering a Next.js client component's bundle.

`DATABASE_URL` configures application queries. `DIRECT_URL` configures migration
commands through `prisma.config.ts`. Neither is required to generate the client
or build the introduction page. Never use a `NEXT_PUBLIC_` prefix for credentials.
The client is generated into ignored `src/generated/prisma/` during `npm ci`,
type checking, and production builds. No install or build command runs migrations.

## Local setup with Docker Engine and Compose

Use Node 24 and run `npm ci`. With Docker Engine and the Compose plugin installed:

```bash
cp .env.example .env.local
docker compose up -d --wait
docker compose exec postgres createdb -U shortlink shortlink_test
npm run db:deploy
npm run db:status
npm run test:integration
```

The `createdb` command is needed once for a new local volume. If the test database
already exists, skip it. The Compose service uses PostgreSQL 17, listens only on
localhost:5432, and keeps data in a named Docker volume. Its published credentials
are for this local environment only. `docker compose down` stops it and preserves
the data. If port 5432 is occupied, change the host port in Compose and all three
local URLs consistently.

If PostgreSQL is already installed, create separate development and test databases
with your local administration tools and set the URLs accordingly. Docker is
optional. Do not copy the local credentials to a hosted database.

Both Prisma config files and the integration runner load `.env.local`, then `.env`;
existing environment variables take precedence. Next.js loads its environment
files itself. Keep actual connection strings in ignored files or environment
settings, never in Git or pull requests.

## Migrations

The committed initial migration creates the link table and unique short-code
index. Apply it to an empty development database with `npm run db:deploy`.
Subsequent schema changes follow this workflow:

```bash
# Edit prisma/schema.prisma, then:
npm run db:format
npm run db:migrate -- --name describe_the_change
npm run db:generate
npm run test:integration
```

`db:migrate` uses `migrate dev` and requires a disposable shadow database, normally
created by the local database role. Inspect the generated SQL before committing.
Never run `migrate dev` or a reset against production. If Prisma requests a reset
of a database with data, stop and inspect the drift before choosing how to fix it.

For a reviewed deployment, set `DIRECT_URL` for the intended environment and run
`npm run db:deploy` as a deliberate release step before deploying code that needs
the schema. `npm run db:status` shows migration state. Preview and production must
use separate databases. There is no automated production migration job yet.

## Verification and isolation

`npm run test:integration` first deploys the committed migrations using
`prisma.test.config.ts`, then runs the Node-based integration suite. It requires
`TEST_DATABASE_URL` and accepts only localhost hosts and database names ending in
`_test`. It never falls back to application or migration credentials.

The tests cover destination persistence and lookup, database-enforced code
uniqueness, a missing code, and transaction rollback. Each run uses distinct codes
and removes only its own rows. It does not truncate tables or reset the database.
Unit tests also cover missing and malformed configuration and rejected test targets.

GitHub Actions uses a separate PostgreSQL 17 service container for integration
tests. The application quality job has no database URLs, checking that generation,
types, and the production build remain independent of a database. This follows
[GitHub's PostgreSQL service guidance](https://docs.github.com/en/actions/tutorials/use-containerized-services/create-postgresql-service-containers).

The local verification environment has no Docker installation. Its database
checks use a temporary PostgreSQL 17.10 cluster downloaded under `/tmp`, without
adding a binary bundle to project dependencies or creating a hosted account. The
Compose file must still be exercised on a Docker-enabled machine or through the
GitHub service setup after pushing.
